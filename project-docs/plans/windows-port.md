# Windows Port — Feasibility Plan

Status: IDEA / PLANNING — nothing here has been implemented. This document exists so a future Windows-porting effort has a starting point instead of re-deriving the constraints from scratch.

## Why this isn't a quick flag flip

`tauri.conf.json`'s `bundle.targets` is `["deb"]` only today, which looks like the only blocker — it isn't. A Tauri app's Windows build links against **WebView2** (Microsoft's Chromium-based WebView, not `webkit2gtk`) and must be compiled with the Windows MSVC toolchain. Neither of those exist in this project's Linux development environment, and there is no reliable way to cross-compile a working, testable Tauri Windows binary from Linux — the practical path is always to build *on* Windows (a real machine, a VM, or CI), never to cross-compile *for* Windows from Linux.

That means this plan can describe the changes needed, but **actually producing and testing a Windows build is out of scope for this environment** until the user has access to a Windows machine or sets up CI (see below).

## What already works in our favor

Exploration of the current codebase found more cross-platform groundwork already in place than the README previously let on:

- `src-tauri/icons/` already contains `icon.ico` (Windows) and a full set of Windows Store `SquareXXXLogo.png` tile sizes, generated by Tauri's own icon tooling — just not referenced by `tauri.conf.json`'s `bundle.icon` array yet.
- `src-tauri/src/main.rs` already has `#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]` — a Windows-only attribute (suppresses a console window in release builds) that only makes sense if Windows was at least considered during scaffolding.
- The only native-dialog dependency, `rfd = "0.14"`, is cross-platform by design — GTK3 on Linux, native Win32 common dialogs on Windows, Cocoa on macOS. No dialog code needs to change.
- Nothing in `Cargo.toml` pulls in a Linux-only crate directly; GTK only comes in transitively through Tauri's Linux windowing backend (`wry`/`tao`), which Tauri itself swaps out per-platform.

## Recommended path: CI-built Windows installer

Set up a GitHub Actions workflow using a `windows-latest` runner that runs the normal Tauri build (`npm install`, `npm run tauri build`) with `bundle.targets` including `"nsis"` (or `"msi"`) for that platform. This is the standard way Tauri projects ship multi-platform releases — the CI runner *is* a real Windows machine, so the resulting `.exe`/installer is a genuinely compiled-and-linkable Windows build, not a cross-compilation guess. The workflow produces a downloadable installer artifact that a real person then needs to actually install and run on Windows to confirm it works — CI can prove it *builds*, not that it *runs correctly*.

## Code changes this plan implies (not done yet)

1. **Scope `GDK_BACKEND=x11` to Linux only.** `main.rs` currently sets it unconditionally:
   ```rust
   std::env::set_var("GDK_BACKEND", "x11");
   ```
   This is harmless on Windows today (Windows reads no such variable), but it's a Linux/GTK-specific workaround (see ADR-003) that should be wrapped in `#[cfg(target_os = "linux")]` once Windows is an actual build target, both for clarity and to avoid any future surprise if GDK-related env vars ever get inspected cross-platform.

2. **Add a Windows bundle target.** Either extend `tauri.conf.json`'s top-level `bundle.targets` to include `"nsis"`, or (cleaner, since the CSP/window config is shared but bundle targets differ) add a `tauri.windows.conf.json` platform-override file, which Tauri automatically merges on top of the base config when building for Windows. Wire up the already-present `icon.ico` and Store-tile PNGs in that config's `bundle.icon`.

3. **Decide how Windows users get `yt-dlp`/`ffmpeg`/`curl` on `PATH`.** The app's whole design assumes these three are external, user-managed binaries already on `PATH` — that model should carry over to Windows rather than switching to bundled "sidecar" binaries as a first step (sidecar bundling is a legitimate stretch goal, but it's meaningfully more packaging work — Tauri sidecars must be architecture-specific binaries checked into or fetched during the build). Simplest first step: document a `winget install yt-dlp.yt-dlp` / `winget install Gyan.FFmpeg` style prerequisite section, mirroring the current Linux "Getting Started" prerequisites step.

4. **Re-check every `std::process::Command` invocation for shell/path assumptions.** `queue.rs` and `lib.rs` invoke `yt-dlp`/`ffmpeg`/`curl`/`df` directly by name (relying on `PATH` resolution, not a shell). This already avoids the most common Windows `Command` pitfall (no shell means no `cmd.exe`-specific quoting to worry about), but `df` (used for the disk-space preflight check) is Unix-only — Windows has no `df` binary. That check will need a Windows-specific implementation (e.g. `GetDiskFreeSpaceExW` via a crate, or shelling out to `powershell -Command "(Get-PSDrive ...).Free"`) rather than assuming `df` exists.

## Testing gap — the actual acceptance bar

Nothing in this plan can be considered "Windows support, done" until someone installs the CI-built artifact on a real Windows machine and confirms: the app launches, native folder picker works, a video actually downloads and merges via `ffmpeg`, and the disk-space check doesn't crash for lack of `df`. Until that happens, treat any Windows build as unverified — the same standard this project already holds Linux-side fixes to in `project-docs/REVIEW.md`.
