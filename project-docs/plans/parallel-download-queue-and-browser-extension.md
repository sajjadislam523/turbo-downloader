# Parallel Download Queue + Browser Extension

Replace the single-download-at-a-time model with a bounded-concurrency queue usable from all three modes (single, batch, keyword), rebuild the UI around a multi-item queue view, and add a Chrome extension that sends URLs to the app via a custom `turbodl://` deep link.

**Status:** IN PROGRESS — Phases 1-3 built and verified (`cargo build`/`cargo test`/`npm run build`/`npm run tauri build` all pass; the deep-link bridge was verified live — cold start, warm-instance handoff, and malicious-payload rejection all confirmed by actually launching the built binary). Phase 2 item 4 (full keyword multi-select) deferred. Phase 4 item 1's backend half (add-batch) is done; its extension-side multi-select UI, plus items 2-4, remain. The Chrome extension itself has not been exercised in a real browser in this environment — see README.md § Browser Extension for the manual install/test steps.

## Background

Today `reserve_download_slot`/`busy: AtomicBool` (`src-tauri/src/lib.rs`) rejects any overlapping download, and batch/keyword modes only download sequentially via `spawn_sequential_downloads`. The "5x parallel" in the UI is yt-dlp's own intra-file fragment concurrency, not multiple simultaneous videos. This plan adds true multi-video concurrency, bulk URL entry from all three modes (not just keyword), and a browser-extension bridge — see ADR-004 for the two key structural decisions (queue/worker-pool model, deep-link bridge choice).

## Phase 1 — Backend queue engine

1. [x] Add `QueueItem`/`QueueState` data model and poison-tolerant lock helpers (generalized from `pid_lock`).
    - Files changed: `src-tauri/src/queue.rs` (new)
    - Expected outcome: queue state compiles and is `.manage()`d, replacing `DownloadState`'s single-slot fields.
    - Deviation from plan: no `uuid` dependency was added — item ids are generated by a simple in-process `AtomicUsize` counter (`next_id`), which is sufficient since ids only need to be unique for the app's current run (nothing persists the queue across restarts in this phase) and avoids a new crate for one-time-per-process uniqueness.

2. [x] Implement the dispatcher thread + per-item worker spawn; factor out `build_ytdlp_command`; delete `spawn_sequential_downloads`.
    - Files changed: `src-tauri/src/lib.rs`, `src-tauri/src/queue.rs`
    - Expected outcome: N `Pending` items run concurrently up to `max_concurrency`, each in its own worker thread.
    - Deviation from plan: the shared streaming primitive is a new `queue::stream_and_wait_item` (emits per-item `queue-item-progress` instead of the old global `download-progress`) rather than reusing lib.rs's old `stream_and_wait`, which was deleted along with `spawn_and_stream` and `start_turbo_download` (all superseded by the queue engine + `enqueue_download`).

3. [x] Implement the per-host concurrency cap + per-host cooldown, replacing the global 4-8s inter-item sleep.
    - Files changed: `src-tauri/src/queue.rs`
    - Expected outcome: same-host items are capped well below `max_concurrency`; different hosts are not throttled by each other.
    - Post-launch fix: the initial cap was hardcoded to exactly 1 in-flight item per host, which meant same-host batches (the common case — most bulk downloads share a host) never actually ran in parallel regardless of `max_concurrency`. Changed to `per_host_cap(max_concurrency) = max_concurrency.div_ceil(2).max(1)`, which scales with the live concurrency setting instead. Reported by the user testing the built app: "selected 4 for the download and added 2 files... one file is downloading and another is pending."

4. [x] Implement the disk-space preflight check before admitting new items.
    - Files changed: `src-tauri/src/queue.rs`
    - Expected outcome: new items fail cleanly with a clear message when free space drops below a floor, instead of corrupting a download.
    - Deviation from plan: no `sysinfo`/`fs4` dependency was added — free space is read by shelling out to `df --output=avail -B1 <dir>`, consistent with this codebase's existing pattern of shelling out to system tools (`curl`, `kill`) rather than adding a crate for one syscall. Fails open (allows the download) if `df` itself can't be read, rather than blocking on an unrelated `df` quirk.

5. [x] Implement per-item cancel, cancel-all, and generalize window-close cleanup to kill every tracked process group.
    - Files changed: `src-tauri/src/lib.rs`, `src-tauri/src/queue.rs`
    - Expected outcome: cancelling one item never affects others; closing the app window leaves no orphaned yt-dlp/ffmpeg processes regardless of how many were running.

## Phase 3 — Chrome extension MVP + deep-link bridge

1. [x] Add `tauri-plugin-deep-link` + `tauri-plugin-single-instance`, register the `turbodl` scheme.
    - Files changed: `src-tauri/Cargo.toml`, `src-tauri/tauri.conf.json`, `src-tauri/src/lib.rs`
    - Expected outcome: the OS recognizes `turbodl://` links and routes them to this app.
    - Deviation from plan: `tauri-plugin-single-instance` is used with its `deep-link` Cargo feature enabled, which makes it automatically forward a second launch's argv into `tauri-plugin-deep-link` (emitting the same `deep-link://new-url` event a cold start produces) — so cold-start and warm-instance links share the exact same downstream event handler in Rust, not just the same validation function. Wiring lives in `lib.rs`'s `run()`, not `main.rs`.

2. [x] Implement `handle_incoming_deep_link` with strict validation (scheme allow-list, leading-dash rejection, size cap) and wire cold-start + warm-instance paths into it.
    - Files changed: `src-tauri/src/lib.rs`
    - Expected outcome: a valid link enqueues; an invalid or malicious one is rejected before reaching any `Command`.
    - Verified live: launched the app, then launched a second process with a malicious payload (`turbodl://add?url=--exec%3Dtouch%2F%2Ftmp%2Fpwned`) — the second process exited immediately (handed off to the running instance, confirming single-instance detection works) and the running instance logged `[deep-link] Ignored an incoming link: value looked like a command flag`; the target file was never created. A second launch with a valid `https://` URL produced no rejection log (silently accepted). Both `add` (single URL) and `add-batch` (repeated `url=` params, capped at 50) hosts are implemented, ahead of the original Phase 4 scope for the backend half.

3. [x] Build the extension MVP: manifest (MV3), background service worker, single-link context-menu send, minimal popup.
    - Files changed: new `extension/` directory (manifest.json, background.js, popup.html, popup.js, README.md)
    - Expected outcome: right-clicking a page or link in Chrome offers "Send to TurboDL," which opens the app (or focuses it) with the URL enqueued.
    - Not independently verified in this pass (no Chrome browser exercised the extension end-to-end in this environment) — the Rust-side deep-link handling was verified directly (see item 2); loading the extension unpacked and clicking through it is still a human-verification step, documented in README.md § Browser Extension.

4. [x] Verify end-to-end (Rust side).
    - Cold-start argv parsing, warm-instance handoff via single-instance, and malicious-payload rejection all verified live (see item 2). Full end-to-end including a real Chrome install is the one remaining manual step.

- [x] Per-item pause/resume. `pause_queue_item`/`resume_queue_item` commands; "Pause"/"Resume" buttons per row in `QueueItemRow`. Relies on yt-dlp's default partial-file resume — no persistence or special resume logic needed.

    - Files changed: `src/App.tsx`
- [x] Fixed the extension never actually opening the app — two attempts, the second confirmed as the likely real fix by isolating the failure with live diagnostics on the same machine as the running app:
    - Attempt 1 (superseded): assumed `chrome.tabs.create` rejects custom schemes; switched to `chrome.scripting.executeScript` injecting `window.location.href`. User reported it still didn't work.
    - Diagnosis: ran `xdg-mime query default x-scheme-handler/turbodl` (correctly resolved) and `gio open 'turbodl://add?url=...'` (correctly launched the app) directly — this is the actual mechanism GTK/Chrome use on Linux, and it works, which proves the OS registration + Rust-side `handle_incoming_deep_link` are both fine and the bug is specifically in the extension's browser-side JS. (A plain `xdg-open` CLI test is a red herring on at least this machine — its desktop-file search path doesn't include `~/.local/share/applications` and it silently falls back to a plain browser instead.)
    - Attempt 2 (current): replaced script injection with a dedicated `redirect.html`/`redirect.js` extension page that `background.js` opens as a new tab — a real page with its own `window`, which both attempts an automatic `turbodl://` navigation and shows a manual "Open TurboDL Ultra" click-through button as a guaranteed fallback (an actual anchor click is the most universally-honored trigger for a browser's external-protocol prompt). Removed the now-unneeded `scripting` permission.
    - Still not independently verified inside a real Chrome (no browser available in this environment) — the manual button exists specifically so there's always one path that works regardless of Chrome-version quirks in the automatic attempt. Added the `xdg-mime`/`gio open` diagnostic steps to README.md's "If it's not working" section so this can be re-diagnosed quickly if it's still not working.
    - Files changed: `extension/manifest.json`, `extension/background.js`, `extension/popup.js`, `extension/popup.html`, `extension/redirect.html` (new), `extension/redirect.js` (new), `extension/README.md`, `README.md`
- [x] Fixed extension downloads always landing in `~/Downloads` instead of the user's currently selected Save To folder. Traced every enqueue path to confirm this was extension-only: single/batch/keyword all pass the frontend's live `savePath` explicitly with every call; the deep-link path is a pure OS→Rust event with no frontend call at all, so it had been hardcoded. Added `QueueState.default_save_path` (a live mirror of the frontend's Save To folder) + `set_default_save_path` command, called from `App.tsx` on mount and on every `savePath` change; `handle_incoming_deep_link` now reads it instead of a constant.
    - Files changed: `src-tauri/src/queue.rs`, `src-tauri/src/lib.rs`, `src/App.tsx`
- [x] UI compaction pass (smaller tabs/buttons/padding throughout, icon-only queue-row actions, single-line header merging Save-To in) in response to feedback that panels were too large and the queue list was barely visible. Verified visually via a screenshot of the user's own live `tauri dev` session after the change (Single mode panel) — Batch/Keyword panels got the same treatment but weren't individually screenshotted (no way to click between tabs in this environment without disrupting the user's live session).
