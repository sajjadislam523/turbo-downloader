## Pending review

- 2026-09-12 (part 3 — Download button froze the whole app for keyword mode): confirmed live by the user — clicking Download made the entire window unresponsive, with the freeze duration scaling with match count. Root cause: `start_keyword_download` is a plain (non-`async`) Tauri command, and Tauri only dispatches a command off the UI/event-loop thread when it's `async` — this command's link-scan fallback can call yt-dlp once per keyword-matching candidate before it returns anything, and all of that ran inline on the UI thread. Fixed by reserving the download slot immediately and moving the probe/scan/download work into a background thread (matching `start_batch_download`'s existing shape), plus a new `keyword-scan-progress` event so the button/status text shows live "Verified X/Y…" progress instead of a frozen message — wired into both the Download flow and "Check Now" (they share the same scanning code). Verified with `cargo test`/`cargo clippy`/`npm run tauri build` and a `npm run tauri dev` launch with no panic, but **not** verified by actually clicking through the flow — same GUI-automation gap noted below for the 2026-09-06 entry (no `xdotool`, no working screenshot tool in this sandbox). Before trusting this: run `npm run tauri dev`, trigger the link-scan fallback with a keyword that matches several candidates, click Download, and confirm the window stays fully responsive (can be moved/resized, Cancel works immediately) while the button/status text visibly counts up instead of sitting on "Preparing queue…"; repeat for "Check Now" to confirm its status text also updates live.
- 2026-09-12 (part 2 — false-positive matches downloaded a listing page instead of a video): confirmed live by the user this time — validation reported matches, but clicking Download tried to hand yt-dlp several `/tag/...`-style listing-page URLs directly, which of course failed with "yt-dlp doesn't support this." Cause: `scan_matching_links` harvested every same-host link whose *text* matched the keyword, without checking whether the link actually pointed to content — a page's own cross-links to other tag/category/"related results" pages have real visible text too (e.g. a "related searches" list) and matched the keyword just as easily as a real video's title would. Fixed with `probe_downloadable`: each keyword-matching candidate is now verified against yt-dlp itself (quick `-j --no-playlist` check, not full download-grade retries) before being accepted as a match. This closes the specific false-positive the user hit, but is still only reasoned through, not re-verified live end-to-end against the same site/keyword that triggered it (this sandbox still has no outbound network access) — if it recurs, check whether `probe_downloadable`'s quick timeout (10s, 1 retry) is too aggressive for a slow site and rejecting genuinely-valid videos as a side effect, before assuming the harvesting logic itself is still wrong.
- 2026-09-12 (part 1, now superseded by the fix above): the user reported the validation error persisted even with the link-scan fallback in place. Root cause I could construct from code review alone (no live network access to confirm): the fallback only triggered when yt-dlp's flat-playlist probe outright *failed*, but yt-dlp's generic extractor can "succeed" on an unsupported listing page anyway (e.g. by picking up an unrelated promotional embed) and report zero real title matches — which took the *original* path's "no matches" error instead of ever trying the fallback. Fixed by making both callers fall back whenever yt-dlp doesn't report a real match, not just on hard failure (`probe_ytdlp_keyword_source`).
- 2026-09-06 (keyword search link-scan fallback): the scraper (`scan_matching_links`/`extract_visible_links`/`find_next_page_link` in `src-tauri/src/lib.rs`) is covered by unit tests against a synthetic listing-page fixture, but has not been exercised against a real, live unsupported site — this sandbox has no outbound network access to test it against one. What's NOT verified: whether a plain `curl` request (no cookies, no consent/interstitial flow, no JS) gets the same HTML a real browser would for a given target site — some sites run bot detection or JS-rendered listings that a raw fetch won't see, in which case the fallback would silently find zero matches rather than erroring. Before trusting this path for a specific site, run `npm run tauri dev`, switch to Keyword mode, paste that site's actual search/tag/category results page URL as Source URL with a real keyword, and confirm "Check Now" returns matches rather than silently zero.
