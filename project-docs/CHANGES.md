## [Unreleased]

- [Fixed] ui: switching mode tabs (Single/Batch/Keyword) and back used to reset the panel you left — every field, including the keyword panel's "Results" count, silently reverted to its default. Each panel was only rendered while its tab was active (`{mode === "keyword" && <KeywordModePanel .../>}`), so React fully unmounted and destroyed its component state on every tab switch; a fresh instance mounted on return with all `useState` back at their initial values. Reported by the user: they queued 3 keyword matches, switched tabs, came back, and it had silently gone back to the default of 5 and queued/started 5 downloads instead. Fix: all three panels now stay mounted permanently in `App.tsx` (toggled with the `hidden` attribute instead of conditional JSX), so switching tabs never loses anything you've typed or an in-flight keyword validation. → see project-docs/plans/parallel-download-queue-and-browser-extension.md
- [Fixed] extension: the extension never actually opened the desktop app — `background.js` tried to trigger the `turbodl://` deep link via `chrome.tabs.create({ url: deepLink })`, but Chrome's tabs API only accepts a small allow-list of URL schemes for programmatic navigation and silently rejects an arbitrary custom scheme like this one; the tab-creation call was effectively a no-op. Fixed by using `chrome.scripting.executeScript` to inject a one-line `window.location.href = deepLink` into the active tab instead — a real page navigating *itself* to an unknown scheme is what actually makes the browser show its external-protocol prompt (the same mechanism `mailto:` links rely on), which `chrome.tabs.create` from a scriptless service worker can't replicate. Added the `scripting` permission; `popup.js` now passes its tab's id explicitly since a popup-originated message has no `sender.tab`. Not independently verified against a real Chrome install in this environment (no browser available here) — reasoned from documented MV3 behavior; please confirm in your own browser. → see extension/README.md
- [Changed] ui: compacted the whole layout in response to feedback that buttons/panels were too large and the queue list was barely visible below the fold — smaller `ModeToggle` tabs, tighter padding/font sizes across all three mode panels (the keyword panel specifically: combined "Check Now"/"Stop" into small icon buttons beside the input instead of a full-width row, clamped the validation message to 2 lines, shows at most 3 sample titles inline instead of a bulleted list), a single-line compact header (title + inline Save-To + icon-only update button, replacing the previous two-row header plus separate full-width Save-To block), and `QueueItemRow`'s action buttons are now small icon buttons (⏸ ▶ ⏹ ✕) instead of text labels. Net effect: substantially more of the window is now given to the queue list itself. → see README.md
- [Added] rust+extension: Chrome extension bridge via a `turbodl://` custom URL scheme — `tauri-plugin-deep-link` + `tauri-plugin-single-instance` (registered with its `deep-link` Cargo feature, so a second-launch attempt on Linux is intercepted and forwarded into the same `deep-link://new-url` event a cold start produces, giving cold-start and already-running cases one shared handler: `handle_incoming_deep_link`). Validates every incoming link independently of how it arrived (OS-level input is attacker-reachable, not just from this app's own extension) — strict `turbodl://add?url=...`/`add-batch?url=...&url=...` parsing, re-validates each URL value via the existing `validate_http_url`, explicitly rejects any value starting with `-` before it can reach `Command::arg` (yt-dlp treats a leading dash as a flag), caps batch size at 50 and total payload at 4KB. Verified live by launching the built app and sending both a malicious payload (confirmed rejected, no side effect) and a valid one (silently accepted) from a second process instance. New `extension/` directory: a Manifest V3 Chrome extension with a context-menu "Send this page/link to TurboDL" and a popup "Send Current Tab" button. → see project-docs/plans/parallel-download-queue-and-browser-extension.md, README.md § Browser Extension
- [Docs] readme: rewrote the architecture diagram, file table, and features table for the new queue engine, and added two new sections — "Concurrent Download Queue" (how the dispatcher/per-host cap/pause-resume work) and "Browser Extension" (install + usage instructions, including what to do if the OS doesn't prompt to open the app). → see README.md
- [Fixed] rust: the per-host concurrency cap was hardcoded to exactly 1 in-flight item per host — since most bulk downloads (e.g. every keyword-search result from one channel) are all the same host, this meant only one item could ever run at a time regardless of `max_concurrency`, defeating the point of the queue for its most common workload. New `per_host_cap(max_concurrency)` scales the cap with the live concurrency setting (`max_concurrency.div_ceil(2).max(1)` — e.g. 2 at the default of 3, 4 at 8) instead of a flat constant, so same-host batches actually run in parallel up to a sensible fraction of the configured limit while still protecting against an unbounded same-host burst. → see project-docs/plans/parallel-download-queue-and-browser-extension.md
- [Added] rust+ui: per-item pause/resume — `pause_queue_item` kills a running item's process group (or, for a not-yet-started item, just marks it `Paused` in place) without touching the queue slot count in a way that blocks other items; `resume_queue_item` flips it back to `Pending` for the dispatcher to re-admit. No special resume logic was needed beyond re-running the identical yt-dlp command — yt-dlp resumes a partially-downloaded file from its own `.part` data by default. A deliberate pause skips the usual same-host cooldown (that delay exists to space out *finished* downloads, not to punish an intentional pause) so Resume isn't stuck waiting. New "Pause"/"Resume" buttons on each running/paused row in `QueueItemRow`. → see project-docs/plans/parallel-download-queue-and-browser-extension.md
- [Added] rust: replaced the single-slot download model (`DownloadState`'s `busy`/`running_pid`, `reserve_download_slot`, `spawn_sequential_downloads`) with a bounded-concurrency queue engine in new `src-tauri/src/queue.rs` — `QueueState` holds a `Vec<QueueItem>` and a live, mutable `max_concurrency` (default 3, adjustable via `set_max_concurrency` at any time, including mid-download); a background dispatcher thread admits `Pending` items up to that limit, capped to one in-flight item per host (independent of `max_concurrency`) with a per-host cooldown after each finish, replacing the old global 4-8s inter-file sleep. Disk space is checked (via `df`) before admitting each item. New commands: `enqueue_download`, `enqueue_urls`, `enqueue_batch_file`, `cancel_queue_item`, `cancel_all_queue_items`, `set_max_concurrency`, `get_queue_snapshot`, `remove_completed_item`, `clear_completed`; new per-item events `queue-item-added`/`queue-item-progress`/`queue-item-status-changed` replace the old global `download-progress`/`download-complete`/`download-partial`/`download-error`/`batch-total`/`batch-item-start`. `start_turbo_download`/`start_batch_download`/`stop_download` are removed outright (single atomic cut-over, not a dual-write period, since the old `busy` flag and the new bounded queue are incompatible admission models); `start_keyword_download` now resolves matches to concrete `(title, url)` pairs (the yt-dlp simulate pass now prints `webpage_url` alongside title) and pushes them as queue items instead of running its own single/sequential download process. Window-close cleanup now snapshots and kills every currently-running queue item's process group instead of one tracked PID. → see project-docs/plans/parallel-download-queue-and-browser-extension.md, ADR-004
- [Changed] ui: `App.tsx` (was ~1560 lines) decomposed into `state/QueueContext.tsx` (queue state + per-item event subscriptions), `components/QueueList.tsx` + `QueueItemRow.tsx` (per-row progress/status/cancel), `components/panels/{Single,Batch,Keyword}ModePanel.tsx`, and shared `components/ui.tsx`. Single mode now accepts multiple newline-separated URLs (switches to a shared-resolution bulk add) and batch mode now accepts pasted URLs as an alternative to a `.txt` file — both route through the same `enqueue_urls` bulk path keyword-mode matches already use, so parallel/bulk downloading is available from all three modes, not just keyword search. The URL-debounce effect's `triggerFetch` is now stabilized (read via a ref inside `SingleModePanel`) with no `exhaustive-deps` suppression needed. Known gap: keyword mode still auto-queues its top N matches rather than offering a full checkbox multi-select list (tracked as a follow-up in the plan file's Phase 2). → see project-docs/plans/parallel-download-queue-and-browser-extension.md
- [Fixed] rust+ui: clicking Download in keyword mode could freeze the whole app window, for a duration scaling with how many videos matched — `start_keyword_download` is a plain (non-`async`) command, and Tauri only runs a command off the UI/event-loop thread when it's declared `async`; this command's link-scan fallback can call yt-dlp once per keyword-matching candidate before it knows what to download, and all of that ran inline before returning anything to the frontend. Restructured to reserve the download slot immediately, then do the probe/scan/download work inside a background thread (matching how `start_batch_download` already reserves up front and backgrounds the rest), returning to the frontend right away. Also added a `keyword-scan-progress` event (emitted once per candidate `scan_matching_links` checks, for both the Download flow and the "Check Now" pre-flight check, which share the same scanning code) so the button/status text shows a live "Verified X/Y…" count instead of a static message for however long a slow scan takes. → see project-docs/sessions/2026-09-12-003.md
- [Fixed] rust: the link-scan fallback no longer treats every keyword-matching link as real, downloadable content — a listing page's own cross-links to other tag/category/"related results" pages have real visible text too and can match the keyword just as easily as an actual video's title, so they were previously harvested as false-positive matches and then failed at download time with the same "yt-dlp doesn't support this" error the fallback exists to avoid. New `probe_downloadable` (a quick, low-retry yt-dlp `-j --no-playlist` check, not full download-grade `RETRY_ARGS`) verifies each keyword-matching candidate is actually downloadable before accepting it. `LinkScanResult` now also tracks `text_only_matches` (candidates that matched by text but failed this check), so the empty-result message can say *why* nothing came back — no links at all, links that didn't match the keyword, or links that matched but weren't real content — instead of one generic message. → see project-docs/sessions/2026-09-12-002.md
- [Fixed] rust: the link-scan fallback now also triggers when yt-dlp *can* enumerate a URL but finds zero title matches (not only on outright "can't enumerate" failure) — yt-dlp's generic extractor can falsely "succeed" by picking up some unrelated single item on an unsupported listing page (e.g. a promotional embed), which previously skipped the fallback entirely and reported a plain "no matches" error even though a link-scan would have found the real content. New shared `probe_ytdlp_keyword_source` (used by both `validate_keyword_source_blocking` and `start_keyword_download`, replacing each one's own drifting probe logic) returns a 3-way outcome (`Matched`/`NoMatches`/`CannotEnumerate`) that both callers use to decide when to fall back. The fallback's empty-result message (`listing_scan_empty_message`) also now distinguishes "this page had no readable links at all" from "it had links, none matched the keyword" instead of one generic message. → see project-docs/sessions/2026-09-12-001.md
- [Added] rust: keyword search now falls back to a generic link-scan when yt-dlp has no extractor at all for a site's own search/tag/category listing pages (only for individual content pages) — new `scan_matching_links`/`fetch_html` (via `curl`) harvest same-host links with keyword-matching visible text from the page itself, following standard pagination markup, then feed the matched URLs to yt-dlp one at a time through the new shared `spawn_sequential_downloads` helper (factored out of `start_batch_download`, which now calls it too). Adds `regex` and `url` dependencies and a `curl` runtime prerequisite. → see project-docs/sessions/2026-09-06-001.md
- [Fixed] rust: keyword search's "Unsupported URL" (and other yt-dlp) failures now surface a translated, actionable message (`translate_ytdlp_error`) instead of yt-dlp's raw stderr — explains that the page/site isn't recognized or has no detectable video, rather than dumping the bare error → see project-docs/sessions/2026-09-06-001.md
